# Design

## Context

See proposal.md - Why. `src/pdf_processing.rs` handles visual-line and page-boundary joining. Its current classifier preserves a small set of listed lexical compounds and removes other hyphens before lowercase continuations. Text output and HTML both depend on these reconstruction decisions. The extraction cache is keyed by `EXTRACTION_PIPELINE_REVISION`.

## Goals / Non-Goals

**Goals:**
- Classify Russian hyphenated compounds and discretionary word breaks using Russian lexical data rather than a list of observed examples.
- Apply one classification consistently in same-page and cross-page reconstruction for text and HTML.
- Keep the result deterministic and usable without network access during extraction.

**Non-Goals:**
- Correct spelling or punctuation outside line-wrap reconstruction.
- Infer intended words when lexical data cannot classify a split.
- Change reconstruction behavior for non-Russian text.

## Decisions

- Bundle the UTF-8 Russian Hunspell `.aff` and `.dic` files from `wooorm/dictionaries` at commit `8cfea406b505e4d7df52d5a19bce525df98c54ab` (BSD-3-Clause terms, attribution and license in `data/russian-hunspell/`). Use the pure-Rust `spellbook` Hunspell-compatible parser so morphology and affix rules work offline without a system library. Record the upstream revision, license, and byte sizes with the files.
- For Russian fragments at a line-ending hyphen, preserve the hyphen when the hyphenated form is lexical and remove it when only the concatenated form is lexical. If both candidates are recognized or neither is recognized, preserve the hyphen as the conservative fallback; this avoids silently corrupting unknown names and words. Continue to join the line fragments without whitespace.
- Keep language-resource lookup behind a small classifier boundary in the PDF processing module. Remove a hyphen only when the concatenated form is recognized and the hyphenated form is rejected. Preserve lexical hyphens and ambiguous or unknown candidates. Both same-page and page-boundary paths, and the text/HTML products, use that shared decision so they cannot diverge.
- Increment `EXTRACTION_PIPELINE_REVISION` when the new behavior ships so cached text generated by the previous classifier is recomputed.
- Prefer bundled lexical data over enumerating compounds in code. An external runtime service was rejected because PDF processing must remain offline; extending the current exception list was rejected because it cannot cover arbitrary Russian text.

## Risks / Trade-offs

- [Lexical data may omit names, rare compounds, or inflections] -> Preserve the hyphen when classification is ambiguous and include representative coverage tests; dictionary data improves general coverage but cannot guarantee every token.
- [Redistribution terms or data size may constrain the source] -> Check license and size before selecting and committing the resource; retain provenance and version information.
- [Additional lookup work may affect large PDFs] -> Load the lexicon once and use efficient membership lookup; measure if the selected representation is large.
- [A changed classifier can alter cached article text] -> Bump the extraction pipeline revision and verify reprocessing behavior.

## Migration Plan

Bundle the selected Russian lexical resource, use it for reconstruction, and increment the extraction pipeline revision in the same release. Existing cached entries will be re-extracted under the new revision. Rollback by reverting the code and resource together and restoring the prior revision behavior.
