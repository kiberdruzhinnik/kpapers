# Marker extraction evaluation

Marker is an optional PDF extraction engine. Pdfium remains the default, and a
feed only uses Marker when its effective selection is `marker`. This page
records the evaluation behind the structured worker contract, the observed
behavior on representative PDFs, and the deployment, licensing and rollback
details operators need before enabling it.

## Evaluation setup

The evaluation used the pinned worker image from `marker_worker/`:

| Component | Version |
| --- | --- |
| Python | 3.12 (`python:3.12-slim-bookworm`) |
| `marker-pdf` | 2.2.0 |
| `surya-ocr` | 0.23.0 |
| `indra-ocr` | 1.1.2 |
| `pdftext` | 0.7.1 |
| `torch` / `torchvision` | 2.7.0 / 0.22.0, CPU wheels |
| Worker mode | `fast` (CPU, OCR enabled) |

The PDFs were generated by `tests/e2e/generate_fixtures.py`, with an additional
image-only scanned page and a mixed page that combines a native text header with
a scanned image body. They cover native text, inline emphasis, a multi-page
article with boundary advertisements, a Sponsr publication page, a
promotional-only PDF, and text that exists only in an image. Real Marker
responses are checked in under `tests/fixtures/marker/`; the worker itself is
not required for the Rust test suite.

The worker returns page-aware JSON containing plain text, bold/italic runs,
font size, vertical gap and left offset. Marker HTML, links, images and
attributes are discarded at the worker boundary. The Rust API validates the
response and then applies the same cleanup, title recovery, classification and
safe-HTML policy as Pdfium.

## Results

| Fixture | Pages | Marker output | Processing result |
| --- | --- | --- | --- |
| Native article (`article-alpha.pdf`) | 4 | Cover advertisement, an empty page, a formatted article page and a closing club advertisement | Boundary pages removed; the empty page is retained; title, mixed bold/italic runs and notice paragraphs are preserved; safe HTML contains no advertisement chrome |
| Scanned article | 1 | OCR recovered the heading and both body lines | Heading becomes `<h1><strong>…</strong></h1>`; body text and first-page classification text are present |
| Mixed native and scanned page | 1 | Native header and paragraphs plus OCR-recovered text in a small embedded image | Both the native text and the small scanned region are retained; the page uses OCR because any embedded image makes the text layer incomplete. Explicit `no_ocr` mode rejects the document |
| Club promotion | 1 | `Join the club today` | First-page text classifies the document as `promotional` |
| Sponsr article | 1 | Sponsr header, author, timestamp, read time, disclaimer and body | Sponsr chrome removed; title recovered from the filename; body preserved |

The native fixture exercises the formatting contract most directly. Marker
reported the article heading at 20 pt, a subheading at 12 pt, and separate bold
and italic runs for the mixed-style line. The resulting HTML contained
`<strong>Bold </strong><em>italic<strong> both</strong></em> styles.` and
`<em>…<strong>красный</strong>…</em>`. Literal Markdown markers such as
`**это не инвестиционные рекомендации**` remain plain text rather than being
interpreted as HTML.

## Empty pages and native text

Marker 2.2.0's document builder leaves `page.children` as `None` for a page with
no output blocks, such as a page containing only a filtered page number. Its
`SectionHeaderProcessor` then raises `TypeError: 'NoneType' object is not
iterable`. The worker normalises that value to an empty list before Marker's
processors run, so the page remains in the document with no lines and the rest
of the PDF is converted normally.

For a PDF whose pages all have a native text layer and no page contains an
embedded image or vector path, the worker uses Marker's text-layer path rather
than OCR. Text on every page is not sufficient on its own: a page can combine a
native header with a small scanned region, or visible lettering drawn as paths.
Without OCR the worker cannot prove an image contains no text, and outlined
vector text may be absent from the text layer. Any image or path object makes
the layer incomplete, regardless of size. Such a document, or one with any
page that has no text layer, uses a dedicated `fast` converter with `force_ocr`
set, so Marker's automatic text-layer decision cannot silently omit content.
If Pdfium reaches the worker's bounded form traversal depth, the worker rejects
the document because it cannot establish whether deeper forms contain images.

Explicitly configuring `MARKER_MODE=no_ocr` does not override this safety
rule. If the native text layer is incomplete, the worker rejects the document
with an extraction failure instead of returning partial content, so the API
retains the prior successful cache. The worker never retries a failed
conversion without OCR.

## Behavior and limits

- Marker extracts every eligible PDF when it is the effective engine,
  including PDFs with a native text layer.
- OCR is selected unless the whole document has a native text layer and no page
  contains an embedded image or vector path. A native header plus even a small
  scanned region or outlined lettering therefore does not suppress forced OCR.
  The persistent Marker E2E test checks native, scanned and vector text from one
  page with the pinned runtime. Explicit `no_ocr` mode fails closed for such a
  document. Forms at the PDF object traversal limit also fail closed.
- Page boundaries are retained, so boundary advertisements and publication
  chrome are removed by the existing rules.
- Fast mode sometimes merges an indented region into one `ListGroup`
  paragraph and may lose its emphasis. The worker restores the source
  text-layer line boundaries and font emphasis, so an indented Sponsr notice
  keeps its paragraphs and mixed bold/italic runs inside one blockquote and
  later body text stays outside it.
- The worker never returns markup. The API escapes text and emits only its
  permitted semantic HTML, so unsafe elements or attributes cannot reach the
  feed.
- If the worker is unavailable, times out, rejects a document or returns an
  invalid response, the document refresh fails. The API does not invoke
  Pdfium and retains the last successfully processed cached content.
- A timed-out conversion schedules a process exit because Marker work cannot
  be cancelled safely. The Compose `restart: unless-stopped` supervisor
  recreates the worker and releases its capacity, including when the client
  disconnected before the timeout response was written.
- Formatting is not byte-identical to Pdfium output. Headings, paragraph gaps
  and emphasis are reconstructed from Marker's line and run metadata, so a
  feed can show small spacing or heading-level differences after switching.
- The CPU image supports `fast` and `no_ocr`. GPU modes (`balanced`, `vllm`)
  require Surya inference-server prerequisites that the image does not include.

## Resource requirements

Suggested minimum for small feeds:

| Resource | Minimum |
| --- | --- |
| CPU | 4 cores |
| Memory | 8 GiB |
| Free disk | 10 GiB for the image and model cache |
| Worker concurrency | 1 |

The first startup downloads Marker's models into the `marker_models` volume and
can take several minutes. With models already cached, the evaluated worker
loaded in roughly 20–30 seconds. The worker health check returns `503` until
models are ready; Compose allows a 15-minute start period.

The defaults bound the work per request:

| Setting | Default |
| --- | --- |
| Input | 25 MiB (`MARKER_WORKER_MAX_INPUT_BYTES`) |
| Response | 8 MiB (`MARKER_WORKER_MAX_RESPONSE_BYTES`) |
| Concurrent conversions | 1 (`MARKER_WORKER_MAX_CONCURRENCY`) |
| Worker execution timeout | 110 s (`MARKER_WORKER_EXECUTION_TIMEOUT_SECONDS`) |
| API request timeout | 120 s (`MARKER_WORKER_TIMEOUT_SECONDS`) |

Concurrent requests beyond the worker limit receive `503`; they are not queued.
Marker is CPU-intensive, so keep concurrency at one unless the host has been
sized and tested for more.

## Enabling and rolling back

Enable the optional worker profile and point the API at it:

```sh
docker compose --profile marker build marker
docker compose --profile marker up -d marker
```

```dotenv
MARKER_WORKER_URL=http://marker:8000
PDF_EXTRACTION_ENGINE=marker
```

Then recreate the API with `docker compose up -d api`. Leaving
`PDF_EXTRACTION_ENGINE=pdfium` keeps Pdfium as the global default while
individual feeds select Marker. See [Deployment with Docker Compose](deployment.md)
for the full startup procedure.

To roll back:

```sh
# Set PDF_EXTRACTION_ENGINE=pdfium in .env and/or select Pdfium in each feed.
docker compose up -d api
docker compose --profile marker stop marker
```

The effective engine and processing revision are part of the cache identity
(`pdf-text-v13:<engine>:<source>`). The next refresh reprocesses affected
documents with Pdfium even when their source fingerprint is unchanged. Cached
content from the last successful extraction remains available while a refresh
fails. Remove the worker with
`docker compose --profile marker rm -sf marker`; remove the `marker_models`
volume only when the model cache is no longer needed.

## Reproducing the checks

Run the worker contract and HTTP tests without Marker installed:

```sh
python3 -m unittest discover -s marker_worker/tests -v
```

Verify the Compose supervisor restarts the worker after a timeout and that the
next conversion succeeds, including after a client disconnect:

```sh
./scripts/marker-supervisor-test.sh
```

Run the Rust tests that consume the real Marker responses:

```sh
cargo test marker_real_
```

Run the full Marker management, extraction, RSS and engine-switching flow in
the isolated Compose stack:

```sh
E2E_EXTRACTION_ENGINE=marker ./scripts/e2e.sh
```

To regenerate the fixtures, start the optional worker profile, post each
generated PDF to `POST /extract`, and save the JSON response under
`tests/fixtures/marker/`. Do not add private or operator documents.
